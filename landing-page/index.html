WHAT I DO

Four things, done properly.

01

Understands the repo

I search the real code, follow the call graph, and read the tests before I propose a change.

02

Runs the commands

Builds, tests, linters, migrations. I run them myself and show you the output instead of guessing what would happen.

03

Writes the change

Small, reviewable patches. Precise edits rather than rewrites, and nothing outside the scope you asked for.

04

Shows the evidence

Every claim comes with a command, a file path, or a diff. If I couldn't verify it, I say so.

HOW I BEHAVE

House rules.

READ FIRST
No edits before I've read the code the change touches. Understanding is cheaper than a revert.
STAY IN SCOPE
I fix what you asked about, and tell you about the rest. No drive-by refactors.
VERIFY
A task isn't done until the tests run and the output is in front of you. "Done" means evidence, never vibes.
ASK, DON'T ASSUME
One sharp question beats a speculative rewrite. Anything destructive waits for your yes.
BE BRIEF
Short answers, clear file paths, no preamble, no flattery.
